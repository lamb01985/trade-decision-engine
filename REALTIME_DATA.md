# Real-time stock data contract

The application uses Massive REST polling. It does not currently use a WebSocket.

## Data path

| Stage | Source and timestamp | Refresh/cache behavior |
|---|---|---|
| Massive adapter | `GET /v2/aggs/ticker/{symbol}/range/1/minute/{start}/{end}` supplies strategy bars; each aggregate `t` is stored as a UTC `Bar.timestamp`. `GET /v2/snapshot/locale/us/markets/stocks/tickers/{symbol}` supplies current-price candidates; `lastTrade.t`, `lastQuote.t`, and `min.t` are parsed independently and the freshest usable priced observation is selected. | REST, 20-second request timeout. No adapter-level cache. |
| Analysis service | Only completed minute aggregates (`bar timestamp + 1 minute <= analysis time`) enter the unchanged decision engine. `decision_bar_timestamp` records the newest strategy bar. The newer of the stock snapshot observation and completed-minute close becomes `current_price` and `provider_timestamp`. | Per-process, per-symbol analysis cache: 60 seconds. Cache hits recalculate age/status at response time. `refresh=true` bypasses it. During a visible regular-session Overview/Levels page the browser force-refreshes every 60 seconds. |
| Decision engine | Receives completed regular-session 1-minute bars; existing resampling produces 5m/15m structure. | No freshness thresholds or setup rules were added to the engine. Freshness gates only `permission_to_trade`. |
| Watchlist scanner | `GET /api/scanner` analyzes up to 30 requested symbols concurrently and returns per-row provider/analysis timestamps and status. | User-triggered. `refresh=true` bypasses analysis cache; otherwise cache is at most 60 seconds and status is recalculated. |
| Live Radar | `POST /api/market-scanner`; symbols run in sequential batches of 8, concurrent within each batch, maximum 250. Every Radar scan forces provider revalidation regardless of the compatibility `refresh` flag. | Browser defaults to 60 seconds **after the prior scan completes**. `radarInFlight` prevents overlaps. Partial failures make the entire scan `ERROR`, suppress candidates and alerts, and list failed symbols. While closed, the same qualification/ranking produces next-session preparation candidates without emitting or advancing live alerts. |
| Overview | Uses `current_price`, `price_source`, provider time, analysis time, age, session, and data status from `/api/analyze/{symbol}`. | User analyze/click refresh plus automatic 60-second force refresh during the regular session. Loading/error states are non-actionable. |
| Levels | Uses the same `SymbolAnalysis` object as Overview. Current price is the snapshot/aggregate observation; setup/structural levels are from the recorded decision bar and both timestamps are shown. | Same symbol and refresh path as Overview; no independent data path. |
| Options plan | Re-runs the underlying analysis server-side with `force=True` before inspecting contracts. | Stale/error underlying data vetoes contract evaluation. Closed-market latest-session data may be researched, but maps to WAIT and never a confirmed live recommendation. Raw option discovery is labeled latest-session when closed and is not an entry authorization. |

## Three separate times

- `provider_timestamp`: when Massive generated the freshest priced underlying observation used for Current Price.
- `decision_bar_timestamp`: start time of the latest completed minute aggregate evaluated by the strategy.
- `analysis_timestamp`: when the engine completed evaluation.
- Display time is generated by the browser when it renders the response; it is never reused as provider or analysis time.
- `data_age_seconds = max(0, floor(now UTC - provider_timestamp UTC))`.

## Existing freshness thresholds and action gate

The existing thresholds remain: `LIVE <= 90s`, `DELAYED <= 300s`, and `STALE > 300s`. They were not loosened. `permission_to_trade`, scanner READY/alerts, and confirmed options recommendations require both `data_status == LIVE` and `market_session == REGULAR`. Closed data can produce WATCH/NEXT SESSION research artifacts only.

The session classifier distinguishes `PREMARKET` (04:00–09:30 ET), `REGULAR` (09:30–16:00 ET, including modeled early closes), `AFTER_HOURS` (close–20:00 ET), and `CLOSED` (overnight, weekends, and modeled NYSE holidays). During `CLOSED`, an available old observation is labeled `MARKET_CLOSED` regardless of its wall-clock age. Historical setup state remains visible but is not actionable.

Maximum expected age while shown as actionable is 90 seconds by definition. A normal Overview refresh occurs every 60 seconds and Radar schedules the next scan 60 seconds after completion. A market-wide scan has no fixed completion guarantee: its upper bound depends on symbol count and provider latency (each REST request has a 20-second timeout), so 100+ symbols cannot be guaranteed to finish inside 60 seconds. If it overruns, scans do not overlap and the page remains REFRESHING/non-actionable until completion.

## Provider-backed verification

Closed-market check (unchanged timestamp/price is expected and accepted):

```bash
.venv/bin/python -m app.live_market_verify --symbol QQQ --wait-seconds 0
```

Run this Monday between 09:30 and 16:00 ET:

```bash
.venv/bin/python -m app.live_market_verify --symbol QQQ --wait-seconds 65
```

The command performs two forced analyses and one forced one-symbol Radar scan using the configured Massive account. During REGULAR hours it passes only when the provider timestamp advances and both analysis and scanner report LIVE. Outside REGULAR hours it explicitly says that unchanged observations do not prove live updating. It never generates or substitutes simulated market data.

## REST versus WebSocket

REST is sufficient for the unchanged completed-candle 1m/5m/15m strategy and a modest watchlist at a one-minute cadence. It is only partially sufficient for a 100–250 symbol universe, tick-level Current Price, and low-latency transition alerts because scan duration and many REST calls can exceed the desired cadence.

A future Phase 2 should stream stock trades/quotes and per-second/minute aggregates for the active symbol and Radar universe, keep REST for bootstrap/history, levels history, option reference, and reconciliation, and only send **completed** candles into the strategy. The stream layer should maintain per-symbol sequence/timestamps, reconnect with exponential backoff and jitter, detect gaps, backfill gaps by REST before declaring LIVE, and suppress actionability through disconnect/recovery. Resource limits and Massive subscription connection/channel limits must be measured before choosing universe size. This is a recommendation only; no WebSocket was added in this pass.

## TradeHub Unified ETF increment

The new authenticated `/api/v1/market-data/{capabilities,snapshot,bars}` routes implement a separate read-only ETF quality contract. They do not replace frozen strategy freshness decisions. Only QQQ/SPY/IWM snapshots and bounded RTH one-minute bars are accepted; daily/options/index/futures resources are not enabled. `app/market_data/sessions.py` pins exchange_calendars4.13.2; `quality.py` uses explicit timestamp units and preserves future-clock errors. Feed recency remains UNKNOWN until approved deployment evidence is integrated. Legacy LIVE verification above does not establish the new quote-pair CURRENT predicate.

When MARKET_DATA_UNIFIED_ENABLED is exactly true, all integrated provider HTTP attempts reserve through a protected shared Redis account policy. Required configuration includes the dedicated MARKET_DATA_SERVICE_TOKEN (at least32randombytes), service URL/profile, Massive account scope, total requests/minute and legacy reserve, plus HTTPS Redis URL/token. Local service HTTP requires explicit APP_STORAGE_MODE=local and literal loopback; hosted uses HTTPS. No real values or shared policy were set by implementation.

Tests use synthetic data; actual deployment-key entitlements, approved recency registration, account quota/reserve, calendar/provider sample comparison, service hosting and a full RTH99percent per-ETF quote-pair measurement remain activation dependencies. See the sibling TradeHub docs/market-data/M2-0-M2-1-IMPLEMENTATION-REPORT.md. No deployment is authorized.
